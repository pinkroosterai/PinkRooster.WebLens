RingBuffer<T>

RingBuffer<T> is a fixed-capacity circular buffer built for scenarios where you need bounded, allocation-free storage that overwrites its oldest entries once full. It implements IEnumerable<T> and ICollection<T>, so it slots into existing LINQ pipelines without adapters.

Unlike List<T>, a RingBuffer<T> never grows past the capacity you give it at construction. Writes past that capacity silently discard the oldest element rather than throwing, which makes the type a good fit for telemetry buffers, recent-event logs, and anything where you only care about the last N items.

Note: RingBuffer<T> is available from Lumen.Collections 2.0 onward. Earlier versions expose the equivalent type as CircularBuffer<T>, which is now marked obsolete.

Overview

Internally, RingBuffer<T> stores elements in a single contiguous array and tracks a head index and a count. Enqueue is O(1) amortised, and Dequeue never reallocates, because the buffer reuses the same backing array for the lifetime of the instance. The type is not thread-safe by default; wrap it in a Lumen.Collections.Concurrent.SynchronizedRingBuffer<T> if multiple threads will write to it concurrently.

Capacity is fixed at construction and expressed in element count, not bytes. Choosing a capacity that is a power of two is not required, but the internal index arithmetic uses modulo division rather than bitmasking regardless of capacity, so there is no performance penalty either way.

var events = new RingBuffer<string>(capacity: 50);

events.Add("startup");
events.Add("connected");
events.Add("first-request");

foreach (var entry in events)
{
    Console.WriteLine(entry);
}

Usage

Construct a buffer with an explicit capacity, then call Add or Enqueue to insert items. Reading the buffer through foreach yields elements from oldest to newest. The Capacity property is read-only after construction; if you need to resize, copy the contents into a new instance with a different capacity.

The TryPeek and TryDequeue methods follow the same try-pattern used elsewhere in Lumen.Collections: they return a bool and pass the element out by ref parameter, avoiding exceptions on an empty buffer. Prefer these over Peek and Dequeue in hot paths where an empty buffer is an expected, not exceptional, condition.

public static RingBuffer<T> CreateWarm<T>(IEnumerable<T> seed, int capacity)
{
    var count = 0;
    var buffer = new RingBuffer<T>(capacity);

    foreach (var item in seed)
    {
        if (count < 10)
        {
            buffer.Add(item);
            count++;
        }
    }

    return buffer;
}
Name Type Description
capacity int Maximum number of elements the buffer can hold.
comparer IEqualityComparer<T>? Optional comparer used by Contains and IndexOf. Defaults to EqualityComparer<T>.Default.
initialItems IEnumerable<T>? Optional sequence used to pre-populate the buffer at construction.
allowOverwrite bool When true (the default), inserting past capacity discards the oldest element instead of throwing.

Performance Characteristics

Benchmarks against a naive List<T>-based ring implementation show RingBuffer<T> allocating zero bytes per operation once warmed up, compared to occasional array copies in the naive version. Throughput on a typical workstation exceeds four million enqueue operations per second for reference types and considerably more for value types, since no boxing occurs.

Memory overhead beyond the backing array is a single object header plus three int fields (head, count, and version, the last used to detect enumeration-invalidating mutations), so a RingBuffer<T> of capacity 1,000 holding reference-type elements costs roughly the same as a plain T[1000] array.

var recentErrors = logBuffer
    .Where(e => e.Level == LogLevel.Error)
    .Select(e => e.Message)
    .ToList();

if (recentErrors.Count > 0)
{
    alertService.Raise(recentErrors);
}

See also PriorityQueue<T> for a bounded structure that orders rather than overwrites, and LruCache<TKey, TValue> for capacity-bounded key lookups with the same non-throwing eviction behaviour.
